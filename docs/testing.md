# テスト方針

## 温度感

個人用の週次バッチであり、間違えたときの損失は「候補リストが変」で済む。網羅率を追う価値はない。
**XBRL 正規化のゴールデンテストと、指標計算の境界値に集中する。**
CLI や出力フォーマットは手動確認で足りる。

## レイヤと優先度

| 層 | 対象 | 優先度 |
|---|---|---|
| ゴールデン | XBRL 正規化（フィクスチャ入力 → `fundamentals` 期待値） | **最高** |
| ユニット | 指標計算（CAGR、利益率、FCF、52週高安、レンジ位置） | **高** |
| ユニット | スロットリング・サーキットブレーカー・時間予算の判断ロジック | 中 |
| 結合 | DuckDB 上のスクリーニング、差分更新、分割検知 | 中 |
| 結合 | 取得ループ全体（偽の HTTP 層に対して） | 中 |
| スモーク | 実 API への疎通 | 手動のみ |

## ゴールデンテストが最優先である理由

XBRL 正規化は**静かに間違う**。落ちるバグなら気づくが、決算期変更で6ヶ月しかない「年度」を
12ヶ月として扱って売上CAGRが1.5倍になっても、例外は一つも出ない。
出力された候補リストを見ても、それが正しいのか判断できない。

Phase 2a で選んだサンプル企業の `companyfacts` JSON をフィクスチャとしてコミットし
（SEC データに再配布制限は無い。詳細は `docs/architecture.md`）、
入力 → 期待する `fundamentals` を固定する。

Phase 2a で決める A〜C の判断ルールには、それぞれテストを置く。

- A：修正再提出をまたぐ企業、決算期変更を経験した企業
- B：YTD しか報告しない企業の Q2/Q3/Q4 変換
- C：複数クラス株の株数

## 指標計算は異常系が本番

「普通のケース」より境界値の方が実際に踏む。

- 分母ゼロ（売上ゼロ、自己資本ゼロ）
- 自己資本マイナス（足切り対象だが、計算過程で落ちないこと）
- 履歴3年未満（最近 IPO → 3年CAGR が計算不能）
- 欠損の伝播（粗利を開示しない企業でトラックB判定が例外にならないか）
- 52週の窓に満たないデータ量

3年CAGR は「累積+33% ≒ 年率10%」の定義で自前計算していることをテストで固定する
（ツールによって定義が違うため。`docs/screening-criteria.md` 参照）。

## 時間依存ロジックは「計算」と「待機」を分ける

スロットリングとサーキットブレーカーは時間依存だが、**時計の注入は不要**。
待ち時間の計算を純粋関数として切り出せば、一度も待たずに検証できる。

```
next_interval(現在の間隔, 結果)  -> 新しい間隔       純粋関数。値を assert する
circuit_state(連続429数)         -> 休止秒数 or None  同上
should_stop(経過秒, 予算秒)       -> bool             同上
```

`sleep` を呼ぶ側は「計算結果をそのまま渡すだけ」の薄い層になり、テスト対象から外す。

特に**時間予算**でこれが効く。「20時間を超えたら打ち切る」を実測で試すと、
設定を0.05秒にしても CI の負荷次第で結果が揺れる。
`should_stop(経過秒, 予算秒)` を切り出せば実時間依存が消え、フレーキーにならない。

取得ループ全体を回すテストでは `config/runtime.yaml` 相当の設定オブジェクトを
**小さい値で直接組み立てる**。パラメータは元々すべて設定ファイルに出す設計なので、
テスト用の特別な仕掛けは要らない。銘柄数を10件程度に絞れば実時間も問題にならない。

## HTTP 層は差し替え可能にする

429 を返す偽のレスポンスでテストするために必要。
これは要件 R5（yfinance → FMP への差し替え）にも要る分離なので、どのみち作る。

## テスト中は外部アクセスを遮断する

`pytest-socket` 等でソケットごと潰す。

- SEC に不要な負荷をかけない（規約の観点でも）
- テストが外部サービスの可用性に左右されない
- うっかり実 API を叩くテストの混入を防げる

実 API への疎通確認は自動テストにせず、`--limit 10` のようなオプションで
少数銘柄だけ走らせる手動スモークテストに留める。

## 合成ユニバースによる条件の回帰テスト

10社程度の架空の財務データを手で作り、「この会社はトラックAを通る／通らない」を固定する。
閾値は何度も調整する前提なので、触ったときに意図しない副作用が出ていないかを検知できる。

## テストで守れないもの

| 守れないもの | 代わりの手段 |
|---|---|
| SEC のレスポンス形式が変わらないこと | Phase 2a の欠損率計測を定期的に回す |
| 実データの数値が正しいこと | 10-K との手動突合（Phase 2b の検証項目） |
| yfinance の仕様変更 | バージョンのピン留め + 手動スモークテスト |

代わりに、**本番コードに実行時のデータ品質チェックを入れる。**
売上がマイナス、自己資本比率が1超、前年比100倍といった異常値を検出してログと通知に出す。
テストで捕まえられないデータ起因の問題は、ここでしか捕まらない。

## 各フェーズの「検証」との関係

`docs/implementation-plan.md` の各フェーズにある「検証」は、**大半が人が目視で行うもの**
（件数のオーダー確認、乖離率の分布、10-K との突合）。自動テストとは区別する。

自動テストにするのは、本ドキュメントのレイヤ表にあるものに限る。
