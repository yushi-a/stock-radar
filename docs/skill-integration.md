# 評価スキル（growth-stock-evaluation）との役割分担

基本思想：スクリーナーは「広く・機械的に・漏らさない」、評価スキルは「深く・一次情報で・判断する」。

| | スクリーナー（本リポジトリ） | 評価スキル |
|---|---|---|
| 目的 | 取りこぼさない | 誤って選ばない |
| 対象 | 全銘柄 → 20〜30件 | 5〜10件 |
| 頻度 | 週次バッチ | オンデマンド |
| データ | API（二次データ含む） | 決算資料・開示書類などの一次情報 |
| 出力 | 候補リスト＋通過理由 | スコア、目標株価、期待倍率、Kill 条件 |
| 判断 | しない | する |

## 設計ルール

1. **スクリーナーの数値は「手がかり」扱い。** 評価スキル側で一次情報から取り直す。両者の乖離が大きい場合はフラグとして扱う。
2. **足切り条件はスクリーナーに一本化。** 時価総額レンジ等の絶対条件はスクリーナーで持ち、評価スキルは「通過済み」を前提にする。
3. **指標選択ルールを揃える。** 評価スキルの margin stage 切替（営業利益率 < −20% は PSR、損益分岐付近は EV/粗利、> 15% は EV/EBIT）をスクリーナーの割安判定にも使う。
4. **期待倍率・スコアはスクリーナーで出さない。** 近似値が判断に流用されるのを防ぐ。

## 連携フロー

```
スクリーニング（週次・全銘柄）
  → 簡易評価（評価スキルの簡潔モード、20〜30件 → 5〜10件）
  → 本評価（評価スキル詳細モード）
```

### トラックA/B でスコアの出方が違う

トラックA候補は、評価スキルの①成長性で構造的に低く出る（3年CAGR 10% の合格ラインが①では3〜4点の帯）。
簡易評価で絞り込むときは、**トラックごとに比べる**。総合スコアを一列に並べると、トラックA候補が理由なく下位に固まる。
経緯と据え置いた理由は `docs/screening-criteria.md` の②。

## 追加で担う役割

- **Kill 条件の監視。** 評価スキルが観測可能な指標（売上成長率、利益率など）で定義した Kill 条件を、保有・ウォッチ銘柄について週次で自動チェックする。
- **フィードバック。** 評価スキルの判定結果を記録し、どの通過条件が高スコアにつながったかを蓄積して閾値調整に使う。

## インターフェース

- スクリーナーは独立ツールとして実装（評価スキルに組み込まない）。
- 評価スキル側には「スクリーナー出力（CSV）を受け取る」入口だけを追加する。
- 出力 CSV の想定列（たたき台）：`ticker, market, name, track(A/B), passed_filters, timing_score, market_cap, revenue_cagr_3y, op_margin, fcf_yield, pbr, psr, range_position_52w, data_source, as_of`
