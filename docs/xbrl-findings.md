## A. 年次レコードの選定ルール

### A-1. `fy` / `fp` は「報告した提出書類」の会計年度であって、データの期間ではない

**サンプル全体で 66%（648/977 エントリ）で `fy` が期間末の年と一致しなかった。**

Apple の例。同じ FY2022（2021-09-26〜2022-09-24）のデータが `fy=2023` と `fy=2024` の両方で出る。

```
2021-09-26..2022-09-24  364日  394,328,000,000  fy=2023 fp=FY filed=2023-11-03
2021-09-26..2022-09-24  364日  394,328,000,000  fy=2024 fp=FY filed=2024-11-01
```

→ **決定：年次レコードは `fy` ではなく `start` / `end` で束ねる。** `fy` は使わない。

### A-2. 同じ期間が1〜5回出る

| 同一期間のエントリ数 | 期間数 |
|---|---|
| 1回 | 104 |
| 2回 | 91 |
| 3回 | 211 |
| 4回 | 12 |
| 5回 | 2 |

元の 10-K に加えて、翌年・翌々年の 10-K の比較欄で再掲されるため。3回が最頻。

### A-3. 修正再提出で値が変わることは実在する

サンプル20社で **55 件**。振れ幅は2種類に分かれた。

| 例 | 変化 |
|---|---|
| AAPL `SalesRevenueNet` FY2009 | 36,537M → 42,905M（**+17.4%**） |
| WMT `Revenues` FY2013 | 468,651M → 469,162M（+0.11%） |

Apple の大きい方は iPhone の収益認識変更（2010年の遡及修正）。
小さい方は表示区分の組み替え。

→ **決定：同じ期間に複数エントリがあるときは `filed` が最新のものを採る。**
「当時報告された値」ではなく「最新の値」を使う。理由は成長率の一貫性で、
3年CAGR を古い基準と新しい基準の混在で計算すると、実態のない成長・減少が出る。
採用した `accn` と `filed` は `fundamentals` に残すので、後から当時の値には戻れる。

### A-4. 期間長は 364 / 365 / 366 / 371 日

10-K に載る売上エントリの期間長（サンプル20社、絞り込みなし）。

| 期間長 | 件数 | |
|---|---|---|
| 62〜98日 | 985 | 四半期（10-K の中にも載る） |
| 184日 | 5 | 半期 |
| 364日 | 198 | 52週決算 |
| 365日 | 547 | |
| 366日 | 189 | 閏年 |
| 371日 | 43 | 53週決算 |

→ **決定：`end - start + 1` が 350〜380日のものだけを年次として扱う。**
設計時に置いた 350〜380 のガードは実測でも妥当だった。**フォームが 10-K かどうかだけでは足りない**
（10-K の中に四半期・半期のエントリが載っている）。

### A-5. 10-K の中の9ヶ月データは決算期変更ではない

母集団のうち **226社**の 10-K に 200〜350日の期間が載っていた。当初これを決算期変更と誤認したが、
中身は比較用の中間期データ（例：IFF の 2024-01-01..2024-09-30）だった。
**350〜380日ガードが正しく除外する。**

本物の決算期変更は **10-KT（移行報告）** で見分ける。母集団の売上エントリでの内訳：

| フォーム | エントリ数 |
|---|---|
| 10-K | 194,791 |
| 10-K/A | 4,269 |
| **10-KT** | **397** |
| 10-KT/A | 6 |

### A-6. ⚠️ 同じ年度が数日ずれた期末で二重に出る（19社）

**設計時に想定していなかったケース。**

```
cik=315189 (DEERE)  2015-10-31 → 2015-11-01  間隔 1日
cik=315189 (DEERE)  2016-10-30 → 2016-10-31  間隔 1日
```

同じ会計年度を、提出書類によって1日違う期末で報告している。
`end` の文字列をそのままキーにすると **1つの年度が2行になり、3年CAGR が1年ずれる。**

→ **決定：年次レコードは期末日そのものではなく、数日の揺れを吸収した会計年度で束ねる。**
実装では「直前に採用した期末から340日未満のエントリは同一年度とみなし、`filed` が新しい方を採る」。

### A-7. 年次期間の間隔（母集団 3,184社）

| 間隔 | 件数 | 意味 |
|---|---|---|
| 1〜14日 | 29 | A-6 の二重計上（19社） |
| 15〜339日 | 115 | 決算期の短縮 |
| 391〜750日 | 163 | 決算期の延長、または1年分の欠落 |
| 751日以上 | 80 | 履歴の断絶 |

→ **決定：3年CAGR は「3行前」ではなく「期末が約3年前（1,000〜1,190日）の年度」で計算する。**
行数で数えると、履歴に穴がある企業で year の数が合わない。条件を満たす年度が無ければ CAGR は欠損とする。

### A-8. BS 項目に `start` は付かない

`Assets` のエントリ **2,383件すべて**が `end` のみだった。

→ **決定：`start` の有無で時点値（BS）と期間値（PL/CF）を機械的に区別する。**

## B. 四半期の YTD → 3ヶ月変換

### 結論：⚠️ **設計の前提が実データと違った。変換はほぼ不要。**

設計（`docs/architecture.md`）は「多くの企業は YTD でしか報告しない」と書いていたが、
**米国 XBRL では3ヶ月値が直接報告されている。**

サンプル20社の 10-Q 売上エントリ：

| 期間長 | 件数 |
|---|---|
| 3ヶ月 | 1,715 |
| 6ヶ月（YTD Q2） | 576 |
| 9ヶ月（YTD Q3） | 559 |

`fp` との対応：

| `fp` | 3ヶ月 | YTD |
|---|---|---|
| Q1 | 560 | —（Q1 は YTD = 3ヶ月） |
| Q2 | 582 | 576 |
| Q3 | 571 | 559 |

**3ヶ月値と YTD が併記されている。** サンプルで 10-Q を出す19社すべてが3ヶ月値を持っていた
（SHPH のみ売上エントリ自体が無い）。

母集団 3,184社での実測：**2,943社（92.4%）が3ヶ月値を直接持つ。**

→ **決定：四半期は期間長 80〜100日のエントリを直接採る。YTD の引き算はしない。**
取れない 7.6% は `revenue_growth_latest_quarter_yoy` を欠損として扱う
（トラックB のこの条件は判定不能になる）。

### Q4 について

Q4 単独の3ヶ月値は 10-K の中に載っている企業が多い（サンプル20社中12社）。
ただし **トラックB が使うのは「直近四半期の前年同期比」だけ**で、年度をまたぐ積み上げには使わない。
Q4 を導出する必要は無いので、`通期 − YTD(Q3)` の実装は不要。

## C. 複数クラス株の株数

### 結論：⚠️ **仮説は当たり。`companyfacts` に軸（dimension）付きファクトは含まれない。**

Alphabet の全エントリに現れるキーを列挙したところ、
`accn / end / filed / form / fp / frame / fy / start / val` のみで、
**軸を表すキーは1つも無かった。**

その結果、株式クラスごとに開示している企業では
`dei:EntityCommonStockSharesOutstanding` が**丸ごと欠落する**。

| 企業 | `dei:EntityCommonStockSharesOutstanding` |
|---|---|
| GOOGL（3クラス） | **エントリなし** |
| RDDT（2クラス） | **エントリなし** |
| FNKO（2クラス） | **エントリなし** |
| BRK（2クラス） | 7件のみ（極端に疎） |
| AAPL（単一クラス） | 70件 |

母集団での出現率も **90.8%** にとどまる。

### 代替：軸なしの全クラス合計が別タグで取れる

| タグ | 出現率 | GOOGL の値 |
|---|---|---|
| `us-gaap:WeightedAverageNumberOfSharesOutstandingBasic` | **97.6%** | 12,125,000,000 |
| `us-gaap:WeightedAverageNumberOfDilutedSharesOutstanding` | **97.4%** | 12,274,000,000 |
| `dei:EntityCommonStockSharesOutstanding` | 90.8% | （なし） |
| `us-gaap:CommonStockSharesIssued` | 89.5% | 12,230,000,000 |
| `us-gaap:CommonStockSharesOutstanding` | 85.4% | 12,230,000,000 |

Alphabet の全クラス合計は約12.2億×10 = 約122億株で、いずれも合計値になっている。

→ **決定：`WeightedAverageNumberOfDilutedSharesOutstanding` を第1候補にする。**
`dei:EntityCommonStockSharesOutstanding` は3番目に落とす。優先順位は `concepts.py` に記載。

### 残る不正確さ（近似で済ませ、フラグを立てる）

- **期中平均であって期末の実数ではない。** 増資・自社株買いの直後はずれる
- **クラスごとに株価が違う。** 全クラス合計 × 片方の株価は厳密には誤り。
  GOOG と GOOGL は1%以内なので実害は小さいが、BRK.A / BRK.B は1,500倍違う（BRK は金融で除外済み）

→ **決定：時価総額は「全クラス合計株数 × 取得した株価」で近似する。**
複数クラス株の銘柄には CSV にフラグを立て、評価スキル側で気づけるようにする。
厳密なクラス別株数が要るなら `submissions` の表紙情報を読む別ルートが必要だが、第一弾ではやらない。

- 売上の欠損 270社の多くは臨床段階バイオ等で、`revenue_positive` でどのみち落ちる

## 🔴 スクリーニング条件の見直し提案（G1）

### 提案：`track_b.gross_margin` はハードフィルタのまま残す

**変更不要と考える。** 理由：

1. 粗利を開示しない業態（電力・航空・飲食・ホテル・石油）は、**そもそも粗利率40%を満たさない**。
   判定不能で落ちても、判定できていても結果は同じ
2. 医薬品・バイオ93社は売上がごく小さく、トラックB（売上YoY 25%以上）の現実的な候補ではない
3. **実質的に取りこぼすのはソフトウェア・データ処理の24社**。母集団3,184社に対して 0.8%

ただし **「粗利不明で判定不能」と「粗利率が閾値未満」を区別して記録する。**
`screen_results` に理由を残し、CSV でも見えるようにする。これが無いと、
取りこぼしが起きていること自体に気づけない。

### 参考：条件を緩める場合の選択肢

ユーザーが取りこぼしを許容しない場合は、以下のいずれか。

- **A案：粗利率を任意条件にする。** 粗利が取れない企業は他の条件だけで判定する。
  → 低採算の業態がトラックB に紛れ込む
- **B案：`OperatingIncomeLoss` ベースの代替条件を置く。** 営業利益率は93.5%取れる。
  ただし「高粗利＝スケールする事業モデル」という趣旨は営業利益率では保てない
- **C案：粗利が取れない銘柄にフラグを付けて CSV には出し、評価スキル側で判断する**
